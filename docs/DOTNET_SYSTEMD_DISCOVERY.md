# Systemd runtime discovery and .NET JSON syntax: governed investigation

Status: opt-in via `AIOPS_DYNAMIC_INVESTIGATION_ENABLED=true`; **read-only**.

## How it works

When a VM service has no registered syntax adapter, the EvidenceCollector asks the
registered `service_runtime_discovery` MCP tool for bounded systemd properties
(`ExecStart`, `FragmentPath`, `WorkingDirectory`, `Type`, startup timeout and
restart policy). No environment values or complete ExecStart arguments are exposed.
The program path must match an absolute executable DLL launched through a .NET host;
unrecognized runtimes remain `unknown`, without guessing paths.

A verified .NET entrypoint is then eligible for `dotnet_config_syntax` on **the
same VM and allowlisted systemd service**. The server derives the publish directory
from systemd again; it never accepts paths or shell commands from incidents, LLMs
or operator input. **No Python must be installed on the target VM.** The remote
VM needs only standard Linux coreutils (`find`, `stat`, `head`, `readlink`,
`base64`) and existing read permissions. A bounded, allowlisted scanner first
identifies regular JSON files and refuses symlinks. For at most 12 files of
up to 1 MiB each, it reads file bytes over encrypted SSH into the trusted
**AIOps VM worker's memory**, where Python performs the syntax validation.

Important trust boundary: secret configuration contents temporarily transit
from VM to the designated AIOps worker over SSH. They are not sent to an LLM,
persisted in PostgreSQL, put in audit events, returned through MCP/API/JSON
responses, or displayed in the dashboard. Operators should approve this
trust boundary before enabling the feature in their environment. The tool
returns only file names, exact line/column and bounded, allowlisted error codes
and Persian descriptions—**not original source lines or secret values**.
The parser tolerates comments and trailing commas in line with typical .NET
configuration JSON behavior, and reports only syntax, not configuration validity.

Outcomes distinguish `syntax_valid`, `invalid`, `partial`, `not_found`
and `unavailable`. For invalid files the result includes filename, line,
column, a non-secret error code and a Persian explanation; unknown/unreadable/symlinked/oversized input is never
mistaken for validated syntax. Syntax-valid JSON is **not** proof of semantic
config correctness, effective environment, successful .NET startup or systemd
readiness. Actual production behavior must still be verified.

The investigator adds these observations to the targeted Cognia query and
to the operator-only incident proposal. In the Incident Command Room the discovered
runtime, DLL, publish location, unit, test outcomes and evidence IDs are shown
without exposing configuration contents or providing an unsafe restart button.

## Security and operational limitations

- The startup `timeout` does not itself identify the cause: check actual
  journal output, systemd `Type`, `TimeoutStartSec`, external dependencies and
  runtime readiness. JSON parse errors and startup failures may coexist
  without being causally related.
- On unsupported non-.NET programs, preserve the information gap; do not mark
  config valid. Add future runtime adapters as typed capabilities, not arbitrary
  model-generated shell.
- **Python is not required on the investigated VM.** The AIOps connector
  must have encrypted SSH read access to the bounded configuration files.
  Unreadable, symlinked, missing or oversized files are incomplete, not valid.
- No service start/restart, file patch, file contents, Diff or rollback is
  generated by these tools. Approval and execution require the existing guarded
  runbook and independent live preconditions.
- Production/staging verification remains **REAL ENV REQUIRED**; tests use
  controlled fixtures and mocks, not the actual GFPAPI server.
- The feature flag is defined in `.env.example` and remains off by default
  until the team's authorized rollout.

## Incident Room operator explanation

The Decision Brief prioritizes the specialized, verified
`dotnet_config_syntax` result over `config_validate supported=false`.
Its Persian operator briefing is derived from durable VM evidence, not model
claims. It separates facts, unknown causation, and change-controlled next steps
and never creates a configuration patch or Start authorization.

The MCP card distinguishes `tool successfully queried` from
`JSON syntax invalid`. Older incidents with only file/line metadata show
that limited diagnosis without inventing missing reasons.
