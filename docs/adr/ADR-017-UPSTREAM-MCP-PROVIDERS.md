# ADR-017 — Upstream MCP Provider Contracts

**Status:** ACCEPTED

## Decision

For the primary observability integrations, the Control Plane SHALL target the actual MCP contracts published by the selected upstream projects rather than project-invented tool names:

- Prometheus: `prometheus/prometheus-mcp`.
- Zabbix: `initMAX/zabbix-mcp-server`.
- Elasticsearch compatibility target: `elastic/mcp-server-elasticsearch`; for Elastic 9.2+ / Serverless, Elastic Agent Builder MCP is the preferred migration target because Elastic has deprecated the standalone repository.

The AIOps domain contracts (`get_metrics`, `get_alerts`, `get_logs`) remain internal and stable. Provider adapters translate those canonical operations into the upstream MCP tool contracts.

## Provider mappings

### Prometheus

Canonical metric evidence -> upstream `range_query` with deterministic PromQL generated by the adapter. Alert evidence -> upstream `list_alerts`.

Allowed read capabilities include `query`, `range_query`, `list_alerts`, `metric_metadata`, `series`, label discovery and health/readiness. Destructive/admin capabilities including series deletion, tombstone cleanup, reload, quit and snapshot are not part of the Control-Plane allowlist.

### Zabbix

Canonical active-alert evidence -> upstream `problem_get`, with bounded `time_from`, search and limit arguments. Optional multi-server routing uses `ZABBIX_MCP_SERVER_NAME`.

Only explicitly selected read-only monitoring tools are allowlisted. Broad/raw or write extensions such as `zabbix_raw_api_call`, `action_prepare` and `action_confirm` are forbidden in the Evidence path.

### Elasticsearch

Canonical log evidence -> upstream `search` using explicit `index`, `fields` and `query_body`. The adapter, not the Agent, constructs the bounded Query DSL and constrains the index using `ELASTICSEARCH_MCP_INDEX_PATTERN`.

## MCP transport requirements

The shared MCP client supports standard Streamable HTTP lifecycle and interoperability requirements used by these upstream servers: `initialize`, `notifications/initialized`, protocol negotiation, optional `Mcp-Session-Id`, JSON responses and SSE responses.

`2025-03-26` is the compatibility baseline because the referenced Elastic standalone server explicitly advertises that protocol version. The client accepts the protocol version negotiated by the server.

## Authentication

Each provider may use a distinct full `Authorization` value:

- `ZABBIX_MCP_AUTH_HEADER`
- `ELASTICSEARCH_MCP_AUTH_HEADER`
- `PROMETHEUS_MCP_AUTH_HEADER`

The generic `MCP_BEARER_TOKEN` remains only a fallback. Write identities remain separate from read identities.

## Security constraints

Agents never receive a raw MCP client and never choose arbitrary remote tool names. They also never supply arbitrary PromQL, Elasticsearch Query DSL or Zabbix raw API calls to an MCP server. EvidenceCollector/provider adapters own deterministic query construction. Mutation capabilities remain behind Decision -> Policy -> Approval -> Execution and require a separate execution identity.

## Deployment acceptance

Production acceptance requires deployment of the chosen upstream MCP servers in the appropriate trust zones, TLS/authentication validation, tool-list/schema verification against pinned upstream versions, and real endpoint tests with least-privilege credentials. Upstream versions/images must be pinned and promoted through the offline software-supply-chain process.
