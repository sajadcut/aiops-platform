# تحلیل عمومی فایل کانفیگ با LLM — مرزهای ایمنی و مسیر اجرا

## هدف

سرویس از نام آلارم حدس زده نمی‌شود: AIOps باید آن را از شواهد رخداد،
MCP و systemd پیدا کند. مسیرهای فایل نیز فقط از `ExecStart`، اطلاعات واحد
systemd، موجودی محدود WorkingDirectory یا مسیرِ تأییدشده توسط Validator
انتخاب می‌شوند. متن آلارم یا LLM به‌تنهایی مجوز خواندن یا نوشتن فایل نیست.

## گردش‌کار

۱. VM MCP با همان هویت SSH فعلی به سرور مراجعه می‌کند و فایل‌های
موجود و خواندنی را در محدودهٔ سرویس شناسایی می‌کند.
برای مرور read-only پسوندهای
`.conf`, `.cfg`, `.cnf`, `.config`, `.ini`, `.properties`,
`.json`, `.xml`, `.yaml`, `.yml`, `.toml`, `.hcl`
شناخته می‌شوند. این فهرست ادعای پشتیبانی اجرایی از همهٔ قالب‌ها نیست.

۲. محتوای واقعی فایل داخل **VM MCP مورد اعتماد** خوانده می‌شود
(حداکثر ۲۵۶ KiB و بدون انتقال به مرورگر یا LLM).
فقط ساختار نحویِ پالایش‌شده شامل شماره‌خط، عمق تورفتگی،
جداسازها، آکولادها و کلمات کلیدی ثابت به مدل داده می‌شود؛
نام‌های دلخواه، مقادیر، نظرات و متن کامل کانفیگ ارسال نمی‌شوند.
فایل‌های ناشناخته یا طولانی ممکن است به علت این پالایش، برای
تشخیص دقیق کافی نباشند؛ در این حالت باید `not_enough_information` گزارش شود.

۳. LLM مرحلهٔ اول نوع خطای احتمالی، شماره‌خط، توضیح و پیشنهاد
را به‌صورت JSON محدود اعلام می‌کند.
در مرحلهٔ دوم، نظر اول و ساختار نسخهٔ پیشنهادی به LLM داده می‌شود
تا دوباره بازبینی کند. اگر هنوز Candidate قطعی در موتور داخلی
ساخته نشده باشد، مرحلهٔ دوم فقط بازاندیشیِ پیشنهاد است؛
**به معنی تست واقعی نسخهٔ اصلاح‌شده نیست**.

۴. در صورتی که یک اصلاح قطعی و ثبت‌شده قابل بازسازی باشد،
AIOps همان پیشنهاد را روی نسخهٔ موقت، نه فایل Production، بازسازی
می‌کند. ویرایش خودکار به‌جای باز کردن تعاملی `vi`، با Patch بایت‌به‌بایت
و Hash انجام می‌شود. تنها پس از تست مستقل Validator قابل‌اعتماد
برای Candidate، درخواست Approval قابلیت تأیید می‌گیرد.

۵. پس از Approval مجزا و تأیید اجرا، مسیر موجود HMAC امضاشده،
تطابق سرویس/فایل/Hash، SSH و sudo، Backup، جایگزینی اتمیک،
تست مجدد و Rollback اجرا می‌شود. LLM هیچ فرمانی را از متن آزاد
به root ارسال نمی‌کند و خود نمی‌تواند مجوز Approval صادر کند.

## دامنهٔ قابلیت کنونی

- **کشف، مرور و دو نوبت تحلیل LLM:** برای همهٔ فرمت‌های بالا، تنها
  در محدودهٔ فایل‌های قابل اثبات یک سرویس systemd.
- **تولید Candidate اجرایی و Apply:** فعلاً فقط الگوهای از قبل
  ثبت‌شده و آزمون‌پذیر مانند اصلاح یک آکولاد اضافهٔ nginx،
  ویرگول انتهایی JSON و تگ بسته‌شدن اضافی XML.
- **HAProxy / Apache / Java / Python / .NET / سرویس ناشناخته:**
  بدون فرض نوع سرویس می‌توان فایل واقعی را پیدا کرد و LLM آن را
  ساختاراً بررسی کند. اما در نبود Parser یا Validator اجرایی
  مرتبط با Candidate نمی‌توان PASS یا امکان Apply گزارش کرد.
  JSON/XML برای سرویس ناشناخته نیز فقط «تأیید ساختار» هستند،
  نه سلامت Startup و تنظیمات برنامه.
- **فایل‌های چندگانه:** چند فایل تأییدشده از systemd مرور می‌شوند؛
  در چت، علاوه بر فایل انتخابی تا سه مورد اول از فهرست
  هم بازبینی LLM می‌شوند؛ این به معنی پوشش صددرصد همهٔ Includeها نیست.

## مشاهده نتایج

در چت رخداد از `service_config_review` یا دکمهٔ بررسی عمومی کانفیگ
استفاده کنید. پاسخ شامل مسیر فایل، یافتهٔ مرحلهٔ اول و دوم،
و عدم قطعیت Validator است. وقتی تحلیل خودکار فعال باشد، نتایج
در `dynamic_investigation.config_llm_review` و Decision Brief
و داشبورد رخداد نمایش داده می‌شوند.

کدها:
`integrations/vm/llm_syntax_projection.py`،
`integrations/vm/general_config_review.py`،
`apps/config_syntax_llm.py`،
`apps/incident_copilot.py`،
`apps/orchestrator/dynamic_investigation.py`.

**قبولی Production:** اجرای تست‌های واحد کافی نیست. باید در یک
VM آزمایشی واقعی ثابت شود که مرور فایل هیچ راز واقعی را به
LLM نمی‌فرستد، Candidate قبل از Approval روی Production
نوشته نمی‌شود، Vendor Validator روی Candidate اجرا می‌شود،
و Apply فقط با Approval معتبر، قفل، Backup و Rollback انجام می‌شود.
سناریوهای محیط واقعی: **REAL ENV REQUIRED**.

## مسیر جدید درخواست صریح فایل کامل به LLM

در چت رخداد با درخواست «فایل کانفیگ کامل را به LLM بده و اصلاح کن»
یا `service_config_llm_repair`، VM MCP ابتدا مسیر فایل مرتبط با سرویس را
از Validator/Systemd تأیید می‌کند، سپس **کل بایت‌های همان فایل** را
در حافظهٔ VM MCP می‌خواند و به مدل پیکربندی‌شده می‌فرستد؛ به‌جای
`value_free_syntax_tokens` متن کامل وارد درخواست می‌شود. پاسخ مدل
باید شامل `corrected_config` با **کل متن اصلاح‌شده** باشد. این مسیر
عمداً جدا از `service_config_review` خودکار/سانسورشده است.

برای فعال‌سازی باید `AIOPS_FULL_CONFIG_LLM_ENABLED=true` در محیط
VM MCP تنظیم و آن سرویس پس از استقرار نسخهٔ جدید راه‌اندازی شود. مقدار
پیش‌فرض `false` است؛ فقط HTTPS یا HTTP لوپ‌بک پذیرفته می‌شود.
**تنظیم این گزینه به معنی اجازهٔ ارسال همه مقادیر فایل، از جمله رمزهای
احتمالی، به LLM انتخاب‌شده است.** بنابراین مقصد باید مورد اعتماد و
دارای مجوز سازمانی باشد. هیچ رمز یا متن کامل فایل به خروجی MCP، تاریخچهٔ
رخداد و رابط کاربری برگردانده نمی‌شود.

این اولین نسخه فقط فایل کامل منتخب تا ۲۴ کیلوبایت را بررسی می‌کند؛
فایل بزرگ‌تر، فایل با کاراکترهای غیرقابل پردازش، یا خروجی ناقص مدل
به‌جای ارسال قطعه‌ای رد می‌شود. هنوز گسترش Includeها به یک درخواست
چندفایلی، نگهداری رمزنگاری‌شدهٔ Candidate، اجرای Validator روی کل
درخت وابستگی‌ها و Apply عمومی پیاده نشده است.
`llm_candidate_proposed` صرفاً پیشنهاد خواندنی است:
`validation_status=UNVERIFIED` و `apply_eligible=false`.
اجرای واقعی و تأیید نهایی صرفاً بعد از پیاده‌سازی و تست گیت‌های مستقل
مجاز خواهد بود. نتیجه در زیرساخت واقعی **REAL ENV REQUIRED** است.
