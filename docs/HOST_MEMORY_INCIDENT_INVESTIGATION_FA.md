# گزارش تخصصی مصرف بالای RAM در Incident Room

## هدف

هشدار High memory utilization (>90% for 5m) یک رویداد **سطح میزبان** است، نه الزاماً اختلال یک سرویس systemd. برای این نوع رخداد، Incident Room کارت **«چرا RAM بالا رفت؟»** را در ابتدای گزارش نشان می‌دهد.

این کارت شواهد را به چهار بخش تقسیم می‌کند: آستانه و Recovery ثبت‌شده در Zabbix؛ اندازه‌گیری مستقیم حافظه و پردازش‌های پرمصرف؛ فهرست بررسی‌های انجام‌شده و انجام‌نشده؛ و اقدامات پیشنهادیِ صرفاً Read-only. اگر علت به شکل مستقل تأیید نشده باشد، گزارش صریحاً «علت ریشه‌ای هنوز تأیید نشده» را نشان می‌دهد.

## جمع‌آوری اطلاعات RAM بدون نصب Python روی VM

ابزار جدید VM MCP با نام memory_diagnostics از SSH فعلی و دستورات ثابت و فقط خواندنی استفاده می‌کند. منابع آن /proc/meminfo، /proc/pressure/memory و ps --sort=-rss هستند. اطلاعات خروجی:

- مقدار MemTotal و MemAvailable و درصد مصرف حافظه
- حافظه Cache قابل‌بازیابی، Swap مصرف‌شده و PSI حافظه
- حداکثر ۱۰ پردازش پرمصرف به تفکیک PID، RSS و درصد RAM؛ بدون argv، اطلاعات محیطی یا Secret

در کنار آن collect_vm_metrics و process_snapshot همچنان امکان ذخیره شواهد مستقل دارند. یک Snapshot، علت رشد قبلی یا Memory Leak را ثابت نمی‌کند.

## شرط اجباری برای اتصال Host RAM Alert به VM MCP

Zabbix باید فیلد یا Tag صریح target_ip را در Webhook ارسال کند؛ HostName و HOST.IP موجود در عنوان/متن هشدار به‌تنهایی مجوز انتخاب مقصد SSH نیستند. IP باید از پیش در فهرست SSH_ALLOWED_TARGETS سمت VM MCP مجاز شده باشد. تا رفع این شرط، گزارش صادقانه «استعلام مستقیم VM انجام نشده» را نشان خواهد داد؛ به هیچ عنوان از نام سرویس unknown یا متن تحلیل Agent برای حدس‌زدن IP استفاده نمی‌شود.

برای رخداد نمونهٔ APORSDTNKSA0101، IP مشاهده‌شده در متن Agent برابر 10.248.41.67 بود، اما لازم است مقدار مجاز و معتبر را از دادهٔ رسمی تیم زیرساخت تأیید و در target_ip Webhook ارسال کنید.

## تفاوت Recovery و اجرای اصلاح

دریافت Zabbix Recovery صرفاً نشان می‌دهد منبع مانیتورینگ رفع هشدار را اعلام کرده است. این پیام نه علت کاهش RAM را ثابت می‌کند و نه Verification اجرای عملیاتی از طرف AIOps است. در نبود اجرای واقعی، بخش «نتیجه اجرا» باید «هیچ اقدامی توسط AIOps اجرا نشده» نمایش دهد.

هیچ Kill، Restart، Drop Cache، تغییر Swap یا افزایش RAM به‌طور خودکار پیشنهاد یا اجرا نمی‌شود. تمام پیشنهادهای جمع‌آوری شواهد فقط Read-only هستند. هر تغییر واقعی به قرارداد اجرایی و Approval مستقل نیاز دارد.

## تست پذیرش واقعی

۱. نسخهٔ جدید API، داشبورد و VM MCP را نصب و راه‌اندازی کنید؛ نصب Python روی VM لازم نیست.

۲. در آلارم RAM، فیلد target_ip معتبر را ارسال و در SSH_ALLOWED_TARGETS تأیید کنید.

۳. یک رخداد کنترل‌شده ایجاد کنید. شواهد memory_diagnostics و process_snapshot باید با زمان و شناسهٔ Evidence در داشبورد ثبت شوند.

۴. کارت «چرا RAM بالا رفت؟» باید منابع معتبر، پردازش‌های پرمصرف، شکاف‌های شواهد و اقدامات اولویت‌دار را نشان دهد.

۵. پس از ارسال پیام Recovery، بخش نتیجه اجرا همچنان نباید موفقیت یک اقدام AIOps را ادعا کند.

نتیجهٔ تست‌های CI جایگزین راستی‌آزمایی روی سرور واقعی نیست. اتصال و جمع‌آوری واقعی برای رخداد تاریخی بدون شواهد محفوظ، REAL ENV REQUIRED است.
