# اتاق فرمان رخداد — طراحی جدید UI/UX تمام‌صفحه

## سناریوی اپراتور ساعت ۳ بامداد

هدف نسخه جدید حذف مدل «جدول در چپ + پنل ریز و پر از تب در گوشه راست» است. اپراتور باید از **Command Center → Operator Attention Queue** یا **Incidents → Incident Workbench** روی یک رخداد در انتظار تأیید کلیک کند و مستقیماً به یک صفحه اختصاصی و خوانا برود:

`/dashboard/incidents/{incident_id}`

این صفحه یک URL مستقل، قابل Bookmark و قابل باز شدن در تب جدید است. مسیر بازگشت `/dashboard?view=incidents` انتخاب صف رخدادها را برمی‌گرداند.

### سلسله‌مراتب دیداری

1. **Hero تمام‌عرض:** سرویس، شرح، Severity، وضعیت، تازگی شواهد، مدت اختلال و نوع تصمیم لازم؛ بدون JSON.
2. **در ۳۰ ثانیه چه بدانم؟** خلاصه فارسی قطعی و شش نکته مهم؛ هشدار شواهد قدیمی/ناقص و تغییر Snapshot در همین بالا.
3. **قبل از تأیید:** Action واقعی، Tool، Target، Risk، Blast Radius، Runbook، Rollback و Verification Plan.
4. **تحلیل و منبع:** Agentها، اطمینان RCA و Evaluator و Agreement مستقل، MCP، مراقبت از خطای داخلی Tool، دانش Cognia و Operational Memory.
5. **بعد از اجرا:** وضعیت Execution مستقل از Verification، Memory و لینک بازبینی دانش در صورت پشتیبانی داده.
6. **زمان‌بندی و تاریخچه:** Audit Timeline و Snapshotهای تاریخی نسخه‌دار و فقط‌خواندنی.
7. **میز تصمیم مستقل:** در نمایش بزرگ در ستون کناری Sticky، در موبایل **قبل از جزئیات** اما **بعد از خلاصه بالایی**؛ دکمه‌ها با چک‌باکس بررسی فعال می‌شوند.

نوع‌بندی فارسی با `Vazirmatn/IRANSans/Tahoma` و اندازه ۱۵px پایه، تیترهای ۲۲ تا ۵۲px، فضاهای سفید کافی، سطح‌های کم‌عمق، کنتراست مناسب و Mobile Breakpoints. انتخاب فارسی/English در `aiops.decision-brief.language` و تم روشن/تیره در `aiops.chatbot.theme` مشترک با Dashboard ذخیره می‌شود.

### امنیت و رفتار واقعی

- **خواندن صفحه GET** فقط همان APIهای دارای مجوز `read:incident` را فراخوانی می‌کند؛ خودش هیچ Workflow یا Tool دارای اثر جانبی را اجرا نمی‌کند.
- **Approve** از `POST /api/v1/approvals/{approval_id}/approve` استفاده می‌کند و بلافاصله عملیات را اجرا نمی‌کند.
- **Reject** دلیل الزامی را از اپراتور دریافت و در API موجود ثبت می‌کند.
- **Resume & Execute** فقط برای Approval با وضعیت `approved` از `POST /api/v1/workflow/e2e/{incident_id}/resume` استفاده می‌کند.
- هر اقدام قبل از POST، مجدداً `decision-brief` و `lifecycle` را می‌خواند و Snapshot، Approval ID و وضعیت را تطبیق می‌دهد؛ در صورت تغییر، چک‌باکس قبلی را بی‌اعتبار و صفحه را Refresh می‌کند.
- ریسک `high` و `critical` تأیید دوم دارند. `binding_complete` و `drift_detected` باعث جلوگیری از اقدام از UI می‌شوند؛ سیاست Backend همچنان منبع نهایی صدور/مصرف مجوز است.
- Snapshot تاریخی صراحتاً بنر هشدار دارد و هنگام مشاهده آن **هیچ** عملیات Approve/Resume/Reject قابل انجام نیست.
- LLM فقط هنگام نمایش گزارش فعلی (نه Snapshot تاریخی) برای prose اختیاری خوانده می‌شود؛ قطع LLM خروجی پایدار را مخفی نمی‌کند.
- Raw Evidence به‌صورت Collapse و درخواست مجزای کاربر است، نه متن خامی که از ابتدا صفحه را اشغال کند. به‌دلیل حساس بودن داده‌های زیرساخت، برای مشاهده آن مجوز `read:incident` لازم است.

## تست مرحله‌ای Windows

بعد از `git pull --ff-only origin main` و اجرای Stack با راهنمای موجود:

```powershell
python -m pytest -q tests/unit/test_incident_command_room.py tests/integration/test_decision_brief_ui_api.py
python -m pytest -q tests
```

1. Dashboard را باز و از صف Incidentها یک مورد `pending` را انتخاب کنید. URL باید به `/dashboard/incidents/<incident-id>` تغییر کند؛ پنل کناری ریز دیگر نباید دیده شود.
2. بدون کلیک، دکمه Approve باید غیرفعال باشد. بعد از تیک تأیید بررسی و تأییدهای لازم، فقط Approval به `approved` منتقل می‌شود؛ هیچ Command نباید در این مرحله اجرا شود.
3. برای اجرای واقعی **فقط روی VM آزمایشی مجاز و Disposable**، دومین تأیید و دکمه `Resume & Execute` را بررسی کنید. پیش‌شرط و Verification باید از Backend معتبر همان Incident بیایند.
4. Reload صفحه / ذخیره لینک / Back/Forward / RTL/LTR / Dark/Light / موبایل / قطع LLM / Evidence ناقص / وضعیت `approved, consumed, rejected` و تاریخی را آزمایش کنید.
5. تغییر برنامه یا Evidence در فاصله بین بارگذاری و POST باید گزارش را تازه و اقدام را متوقف کند؛ Backend هم به‌طور مستقل سیاست Snapshot و Approval یک‌بارمصرف را اعمال می‌کند.

**REAL ENV REQUIRED:** مرورگرهای واقعی، زمان ۳۰ تا ۶۰ ثانیه با اپراتور شب‌کار، دستگاه موبایل واقعی، اتصال Dotin/Cognia/MCP و اجرای واقعی روی VM باید در محیط مجاز جداگانه پذیرفته شوند. Node DOM runtime و CI، معادل تست UX با انسان یا Production E2E نیستند.

## مرتب‌سازی و حالت نمایش رخدادها (۱۴۰۵/۰۷)

در `Dashboard → Incidents` یک کنترل مرتب‌سازی وجود دارد:
- «جدیدترین رخدادها»: بر اساس `started_at` و در نبود آن `created_at`، نزولی
- «قدیمی‌ترین رخدادها»: همان مبنای تاریخ، صعودی
- «نیازمند اقدام فوری»: ابتدا وضعیت Approval و Severity، سپس تاریخ جدیدتر

رخدادهای بدون تاریخ معتبر در انتهای هر ترتیب قرار می‌گیرند.
فیلتر «فقط رخدادهای فعال» پیش‌فرض است؛ «همه رخدادها» موارد بسته‌شده و رفع‌شده را نیز نمایش می‌دهد.
سه حالت نمایش «آیکون بزرگ / متوسط / کوچک» در دسترس است. این دو تنظیم در
`localStorage` مرورگر با کلیدهای `aiops.incidents.sort` و
`aiops.incidents.size` ذخیره می‌شوند و دسترسی به گزارش اختصاصی
`/dashboard/incidents/{id}` در تمام حالت‌ها حفظ می‌شود.

## زبان فارسی قابل‌فهم در گزارش

عنوان قدیمی «در ۳۰ ثانیه چه بدانم؟» حذف و عنوان «خلاصه وضعیت و پیشنهاد AIOps» جایگزین شده است.
خلاصه اصلی گزارش بر اساس مشاهدات معتبرِ ذخیره‌شده نوشته می‌شود. عملیات‌های شناخته‌شده
مانند `start_service` با توضیح روشن فارسی و نام فنی داخل پرانتز نمایش داده می‌شوند.
متن‌های انگلیسی Agent، MCP و Cognia که ترجمهٔ قابل‌استناد ندارند به جای ترجمهٔ ساختگی،
با خلاصهٔ قابل‌پشتیبانی همراه می‌شوند و متن اصلی در «متن تخصصی اصلی» قابل مشاهده است.
شناسه‌های طولانی شواهد نیز در بخش بازشدنی «دیدن شناسه شواهد» قرار دارند.

این اصلاح **صرفاً Presentation** است: نه شواهد، نه درصدها، نه تصمیم‌های Agent و
نه Approval/Execution Binding بازنویسی نمی‌شوند. اطلاعات ناموجود یا علت تأییدنشده
نباید قطعی جلوه داده شوند. بررسی شواهد تازه پیش از تأیید همچنان ضروری است.


## تب آلارم دریافتی

در صفحه مستقل `/dashboard/incidents/{id}` تب «آلارم دریافتی» کنار «خلاصه تصمیم» اضافه شده است. این بخش هیچ ابزار MCP، اجرای عملیات یا مدل LLM را فراخوانی نمی‌کند؛ فقط Evidence ثبت‌شده هنگام دریافت Signal را از API دارای احراز هویت زیر می‌خواند:

`GET /api/v1/incidents/{incident_id}/received-signals?limit=100`

این تب برای هر سیگنال واقعی منبع، نام Zabbix / Prometheus (Alertmanager) / Elasticsearch (ELK)، شناسه، زمان ثبت و زمان رخداد، متن پیام و جزئیات فنی ثبت‌شده را نشان می‌دهد. Zabbix: `tags` و متن `message/name`؛ Prometheus: `labels` و `annotations`؛ ELK: Rule، Alert، Anomaly و تگ‌ها. در صورت Correlation چندمنبعی، پیام‌های مستقل هر منبع در کارت‌های مجزا نمایش داده می‌شوند. Recovery به‌عنوان پیام جداگانه متمایز است.

نسخه‌های جدید پیام دریافتی را با `_received_payload` در Raw Evidence، بعد از Redaction و تنها تا سقف ۶۴ کیلوبایت JSON، ثبت می‌کنند. برای داده‌های قدیمی یا پیام‌های بسیار بزرگ که نسخه اصلی وجود ندارد، رابط با برچسب «نسخه نرمال‌شده» ظاهر می‌شود؛ متن دقیق اولیه یا قالب byte-for-byte ادعا نمی‌شود. اطلاعات محرمانه و Secret-tagها پنهان می‌شوند، کل JSON با جزئیات قابل مشاهده و کپی است. این نمایش صرفاً جهت تصمیم انسانی و بررسی منشأ آلارم است و تأیید یا اجرا را خودکار نمی‌کند.


## رفع انتساب اشتباه آلارم‌های عمومی سرور به nginx (۱۴۰۵/۰۷/۲۰)

در لاگ واقعی، Zabbix با `eventid=136247345` هشدار `Filesystem /` و با
`eventid=136249812` هشدار `Memory` فرستاده بود؛ هیچ‌کدام `service` مشخص
نداشتند، ولی `correlation_key` با پیشوند `nginx` ثبت شده بود. علت: پاسخ
عمومی/کم‌ارتباط Cognia می‌توانست یک فیلد `service` نداشته در Alert را پر کند،
و کد `SignalGateway` حتی در نبود سرویس واقعی، Host را هم جای Service می‌گذاشت.

قانون جدید برای مسیر Signal Ingestion:
- `service` صریح و معتبر از payload/Tag معتبر Zabbix یا label منبع همیشه مبنای هویت است.
- پیشنهاد `service` از Cognia تنها وقتی می‌تواند هویت اولیه را تکمیل کند که
  FQDN داخل **خود سیگنال** با FQDN صریح سند بازیابی‌شده دقیقاً برابر باشد؛
  این حالت همچنان برای اقدام اجرایی نیازمند راستی‌آزمایی زنده است.
- برای CPU/RAM/Disk/Filesystem بدون سرویس صریح و بدون تطابق FQDN،
  `service=unknown`، `correlation` بدون سرویس و `unverified_knowledge_service_hint`
  صرفاً به‌عنوان اطلاعات غیرقطعی باقی می‌مانند. Host به‌جای Service ثبت نمی‌شود.
- صفحه رخداد، در نبود نام سرویس، `هشدار سرور: <hostname>` را به‌جای نام
  ساختگی نمایش می‌دهد؛ این فقط fallback نمایشی است و به execution target تبدیل نمی‌شود.

**محدودیت داده‌های قبلی:** این اصلاح بر رخدادهای **جدید** اعمال می‌شود.
رکوردهای قبلاً درج‌شده با سرویس اشتباه (از جمله nginx) بدون بررسی منشأ و
تصمیم اپراتور به‌صورت خودکار در PostgreSQL تغییر نمی‌کنند؛ زیرا می‌تواند
تاریخچه شواهد/Correlation/Approval را ناسازگار کند. بازبینی باید با
`Dashboard → Incidents → آلارم دریافتی` و بررسی `Evidence` انجام شود.


## الگوی جدید گزارش فارسی و مبتنی بر شواهد

در بخش ۰۱، نتیجهٔ اصلی برای اپراتور اولویت دارد. اگر Validator
اختصاصی سرویس مانند `dotnet_config_syntax` خطای معتبر پیدا کند،
داشبورد باید مسیر واقعی فایل، شماره خط/ستون (در صورت ثبت)، توضیح امن
نوع خطا، موارد تأییدشده، ابهام علت ریشه‌ای، و اقدام پیشنهادیِ غیر اجرایی
را نشان دهد. کلمهٔ «موفق» دربارهٔ فراخوانی MCP به معنی
`syntax_valid=true` نیست.

گزارش تفصیلی SRE، جدول Evidence و شناسه‌ها همچنان در صفحه موجود
هستند، اما پشت بخش‌های بازشونده قرار می‌گیرند تا خروجی تکنیکی
تکراری، جواب اصلی را پنهان نکند. تحلیل فارسی اختیاری LLM (اگر واقعاً
تولید و با شواهد منطبق شده باشد) در کنار خلاصهٔ قطعی نمایش داده می‌شود؛
نبود LLM موجب حذف گزارش قابل‌خواندن نمی‌شود.

### خطای JSON در برنامه‌های .NET بدون نیاز به Python روی VM

بررسی خودکار برنامهٔ .NET باید از `service_runtime_discovery` و
`dotnet_config_syntax` استفاده کند. فایل‌های محدود و مجاز
`appsettings*.json` از مسیر واقعی Publish با SSH فقط‌خواندنی دریافت
و در حافظهٔ Worker پایتونی خود AIOps تحلیل می‌شوند. نصب Python، jq،
SDK یا افزونه روی سرور هدف لازم نیست. محتوای واقعی تنظیمات، کلیدها،
مقادیر و Secretها نباید وارد Evidence، LLM، داشبورد یا لاگ شوند.
خروجی امن شامل کد خطا، توضیح فارسی، فایل، شماره خط و ستون است.

برای Incidentهای قدیمی که فقط خط و ستون ذخیره شده‌اند ولی نوع خطای
Parser ثبت نشده است، نوع خطا را حدس نزنید. باید اعتبارسنجی read-only
تازه انجام شود. خطای Syntax واقعی لزوماً ثابت نمی‌کند علت Timeout همان
خطا بوده است؛ اصلاح کانفیگ، تست مجدد، شواهد تازه، Approval مستقل و
Verification برای هر عملیات ضروری است.
